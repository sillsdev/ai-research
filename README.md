# SIL AI Engineering Research

The [public website](https://sillsdev.github.io/ai-research/) for SIL AI Engineering's research studies, built with [Quarto](https://quarto.org) and published to GitHub Pages.

## Publishing a study

Open Claude Code in this repository and ask it to publish a study, naming the harness and the findings or experiments, for example:

> Publish a study of chrF-B from bt-metric, covering PLAN.md sections 4.1.1 and 5.

The `publish-study` skill walks through it: it pins the harness commit, builds the data summary, drafts the write-up for you to edit, checks it, and opens a pull request. Each harness has its own skill (`.claude/skills/harness-*`) saying where its results are and what must be anonymized. Results from no harness, or from a temporary one, are published as a one-off study (below).

### Step by step

**Once, to set up:**

1. Install [uv](https://docs.astral.sh/uv/), [Claude Code](https://claude.com/claude-code) and the [GitHub CLI](https://cli.github.com/).
2. Clone this repository, and clone the harness repositories you publish from beside it (`../bt-metric`, `../silnlp`, `../bt-checking-eval` with `../bt-checking-eval-data`). For silnlp, mount the experiment bucket and set `SIL_NLP_DATA_PATH` to it.
3. Run `uv sync` in this repository.

**For each study:**

1. **Start from the latest site.** Run `git switch main` and `git pull`, then open Claude Code in this repository.
2. **Ask for the study.** Name the harness and the findings or experiments it covers, for example:
   > Publish a study of chrF-B from bt-metric, covering PLAN.md sections 4.1.1 and 5.

   > Publish a study comparing silnlp's remote LLM translation, with in-context examples, against fine-tuned NLLB across languages.

   > Publish a one-off study of the tokenizer results in my spreadsheet; there's no harness.
3. **Answer its questions.** It asks what question the study answers, what you conclude, which material it covers, and who the authors are. The conclusions come from you or your written findings, not from Claude's reading of the numbers. A one-off study also asks where the results came from, whose data they are, and what could identify a project.
4. **Approve the data.** Claude writes `sources.yml` and runs `rs-import` to build `data/metrics.csv`. The tables in `sources.yml` say which rows and columns of which results files become the study's numbers, and what public names they get. For a private harness, the tables go instead in a **recipe**: a file kept with the private data, because its file paths and label mappings would reveal the real projects, and `sources.yml` only points to it (see [Private repositories](#private-repositories) and [Experiment bucket](#experiment-bucket)). For bt-checking-eval, review and merge the recipe's pull request in the data repository, then Claude pins the merged commit. For the experiment bucket, Claude writes the recipe in the bucket and freezes the files it reads.
5. **Edit the draft.** Claude writes `index.qmd` in the structure of the worked example. Rewrite it in your words, and check every claim against the tables. A number that isn't in the data is marked `<!-- REVIEW: ... -->` with where it came from: add it to the harness's results and import it, or take it out.
6. **Check it.** Claude runs the harness's anonymization pass and `uv run rs-validate studies/<slug>`, then renders the page. Look at it yourself with `uv run quarto preview studies/<slug>/index.qmd`.
7. **Open the pull request.** When you're happy, Claude commits to a `study/<slug>` branch and opens a pull request listing what it anonymized and any open REVIEW notes. CI validates and renders the site on the pull request.
8. **Get it reviewed.** A second person reads the rendered page (checking out the branch and previewing it) for accuracy and for anything that could identify a project. Nothing is public until they approve.
9. **Merge.** Merging to `main` deploys the site within a few minutes, at `https://sillsdev.github.io/ai-research/studies/<slug>/`.

To change a published study later, follow the same steps on a new branch: re-import if the data changes, and the pull request shows the difference.

**Without Claude Code:** copy `studies/2026-10-chrf-b` to `studies/YYYY-MM-<slug>/`, read the skill files in `.claude/skills/` for your harness's rules, write `sources.yml` and run `uv run rs-import studies/<slug>`, write `index.qmd`, then run `uv run rs-validate` and preview before opening a pull request.

### Study folders

A study is a folder `studies/YYYY-MM-<slug>/`:

| File | What it is |
|---|---|
| `index.qmd` | The write-up, with code cells that draw tables and charts from the data |
| `sources.yml` | Each harness repository, its pinned commit and its visibility. For a public repository, also which rows and columns of which results files to use |
| `source/` | One-off studies only: the results summaries, copied in already anonymized |
| `data/metrics.csv` | Generated by `uv run rs-import studies/<slug>`. One row per number: `system`, `group`, `measure`, `value`, `lower`, `upper`, `n`, plus its source and, for a public source, its file |

### Private repositories

For a private repository, the tables live in a **recipe** inside that repository, not in `sources.yml`, which only points to it (`recipe: published/<slug>.yml`). The recipe names private files and maps real project codes to public labels, so publishing it would undo the anonymization. A recipe can share label files, so a project keeps the same label in every study. The study page says the results come from an internal repository at a given commit, without linking to it.

### Experiment bucket

The experiment bucket (`bucket: true`, read from `SIL_NLP_DATA_PATH` or `--bucket-root`) has no commits, so it is pinned by content. Its recipe lives in the bucket under `MT/published/<slug>/`. `rs-import --freeze` copies every file the recipe reads into a `files/` folder beside it and records a `snapshot` hash in `sources.yml`. Later imports read only those copies and fail if the hash changes, so re-running or moving an experiment can't change a published study.

### One-off studies

A study with no harness skill sets `harness: none` and keeps its results summaries in its own `source/` folder, declared in `sources.yml` as `in-study: true` with an `origin` saying who produced them, how and when. A pinned repository could be deleted, which would break every later deploy, so the copies, already anonymized, are what the study rests on. The publish-study skill's `one-off.md` gives the default anonymization rules and what to ask the researcher first.

`studies/2026-10-chrf-b` is the worked example.

## Working locally

Requires [uv](https://docs.astral.sh/uv/). Quarto comes in as a Python package, and harness checkouts are expected beside this repository (`../bt-metric` and so on).

```
uv sync
uv run rs-import studies/<slug>     # rebuild a study's data/metrics.csv
uv run rs-validate                  # the checks CI runs
uv run rs-check-bucket studies/<slug>  # search a bucket study for real project codes; needs the bucket
uv run quarto preview               # live preview; the URL is printed when it starts
```

## What CI checks

`main` is protected: every change goes through a pull request, which needs an approving review from someone other than its author and a passing build before it can merge. Every pull request runs `rs-validate` and renders the site; merging to `main` deploys it. The validator blocks:

- missing front matter, data or sources, and sources not pinned to a GitHub repository and commit
- a source marked public whose repository isn't (checked against GitHub), and a private source's tables or file paths in the public files
- file types other than text and images, files over 500 KB and data over 5,000 rows, since a study holds summaries only
- country names, unless listed under `allowed-terms` in the study's front matter
- unresolved `<!-- REVIEW: ... -->` notes, which mark numbers that don't come from the data

CI can't see a harness's private project codes or corpus, so it backs up the harness skill's anonymization pass rather than replacing it. Before the pull request is opened, the harness skill also runs an identifier check that reads the real project codes from the private data and searches the study for them: `check_provenance.py` in bt-checking-eval, and `uv run rs-check-bucket studies/<slug>` for the experiment bucket. A reviewer approves every study before it goes public.
